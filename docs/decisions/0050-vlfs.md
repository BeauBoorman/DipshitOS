# ADR 0050: VLFS — a journaled guest filesystem on a dedicated virtio-blk disk

- Date: 2026-10-15
- Status: **Accepted** — VLFS is the guest disk: the M100 arc (#2302)
  landed this format as v1. ADR 0061 (card #3028) extends it with the
  sealed v2 format; this document remains the v1 authority.
- Related: ADR 0007 (syscall ABI; M66 slot-77 durability row), ADR 0010
  (file handle ABI), ADR 0013 (pre-exit arming discipline), ADR 0024
  (trust baseline), M66b (`vi.WriteFileSafe`), ADR 0061 (sealed VLFS
  v2 — the encryption layer above this format).

> `kernel/src/file_table.zig`'s own header states today's world: after
> M34 HF6 "the `.host` share (`--cvc-file`) is the ONLY file partition" —
> the host file channel is the guest's storage. `fat32_ro.zig` repeats it:
> "the host file channel (queue 5) is the guest's storage and it stays
> FAT-free." VLFS gives the guest a disk of its own: a small journaled
> filesystem on a dedicated virtio-blk image where crash recovery is the
> point of the exercise, not a footnote. Bounded beats general — one
> volume, one journal, named refusals, a format small enough that
> `fsck.vlfs` is a card and not a career.

## Grounding (observed in tree `d7f950c3` / verified `898e6d4f`, 2026-10-15)

**Observed** means checked in the tree or in the Xcode 27 SDK headers on
this host; **inferred** means reasoning only.

- **No guest-writable block device exists (observed).** M34 HF6 deleted
  the virtio-blk transport, `fat.zig`, and the ESP/DATA partitions
  (`kernel/src/main.zig:332` — "the virtio-blk transport and the ESP/DATA
  FAT partitions are GONE"). The only block stack in-tree is
  `kernel/src/usb_msc.zig` (BOT+SCSI over xHCI, gated on `--usb-msd`);
  it speaks WRITE(10) and a live gate observed a byte-exact sector
  write/read-back (hardware contract, claim #1044), but the `.usb`
  file-table partition built on it is read-only. `fat32_ro.zig` is a
  read-only FAT32 reader for USB MBR partitions — it never touches the
  boot volume and VLFS must not entangle with it.
- **Every boot already has one virtio-blk device: the boot image
  (observed).** The runner always assigns `config.storageDevices =
  [VZVirtioBlockDeviceConfiguration(attachment: …)]`
  (`host/vm-runner/Sources/VMRunner/main.swift:1813,1845`) — under
  `--overlay-base` a read-only base + ASIF overlay stack, otherwise a
  plain read-write `VZDiskImageStorageDeviceAttachment`. The boot volume
  is a single GPT FAT32 ESP (~33.7 MiB floor) parsed by Apple's firmware
  only; no guest code touches it post-exit (hardware contract, M34 HF6
  row). A data disk is therefore a **second** PCI function with the same
  DID 0x1042 (claim 6420's virtio-blk DID), not a new device type.
- **PCI setup must run PRE-EXIT (observed).** `kernel/src/pci.zig:10` —
  config-space and BAR reads after ExitBootServices hang on VZ (claim
  0013); every driver does discovery + capability walk + feature
  negotiation + queue setup pre-exit, then re-arms post-MMU because VZ
  resets virtio devices at ExitBootServices (`virtio_net.zig:17-18`,
  `virtio_entropy.zig`; the claim-6420 lesson). "Post-exit queue
  bring-up" is not available; the blk driver follows the same pattern.
- **The runner can already attach a second block device (observed +
  SDK).** `VZVirtioBlockDeviceConfiguration.blockDeviceIdentifier`
  (macOS 12.3+, ≤ 20 ASCII bytes) is "retrieved in the guest via a
  VIRTIO_BLK_T_GET_ID request" (Xcode 27 SDK
  `VZVirtioBlockDeviceConfiguration.h`). `VZDiskImageStorageDeviceAttachment`
  has an init taking `cachingMode:` and `synchronizationMode:` (macOS
  12.0+; `VZDiskImageStorageDeviceAttachment.h`): sync mode `.full` is
  documented "No synchronized data is lost on panic or loss of power."
  The URL attachment supports **RAW images only** and requires the file
  size be a multiple of 512 bytes (same header).
- **`VZUSBMassStorageDeviceConfiguration` cannot carry a VLFS image
  (observed).** The hardware contract records that VZ's disk-image
  sniffer **refuses a fully-zeroed raw image AND a bare 0x55AA MBR** —
  it demands parseable disk structure. Each `--usb-msd` disk also gets
  its OWN XHCI controller, and the single-controller guest XHCI driver
  probes exactly one, so a combined `--input --usb-msd` boot can hide
  the disk behind the controller the probe did not pick.
- **I/O is polled (observed).** `virtio_custom.wait(queue, handle,
  budget, reply_buf)` scans the used ring for a matching element handle;
  completions may arrive in any order. Existing budgets:
  `cv_log_budget` = 16,000,000, `tee_budget` = 4,000,000 polls
  (`virtio_custom.zig:1196,1248`). No virtio driver's used-buffer IRQ is
  in production on this platform.
- **The file ABI needs no new slots (observed).** Slots 23–27 (open/
  read/write/close/dirlist), 34–36 (delete/rename/truncate), 77 (fsync)
  and 69 (chmod) all route through `file_table.parse_path`'s mount-
  prefix canon (`file_table.zig:1074-1136`): `/host…` → `.host`,
  `usb<N>…` → `.usb_fat`, `usb…` → `.usb`, `/dev/tty` → `.tty`.
  `Partition` is a closed enum (`file_table.zig:78-95`); VLFS adds a
  `.disk` variant. Slot 79 (`fs_metadata.zig`) requires a `Backend`;
  adapters without pinned-lookup `ContainedOps` return
  `ContainmentUnavailable` honestly.
- **The durability contract is already shaped (observed).**
  `vi.WriteFileSafe` (`user/go/vi/vi.go:706`) is temp + fsync-before-
  close + delete-then-rename; the `/host` rename refuses a live target
  (-9 EEXIST), so the publish sequence is delete-then-rename and the
  honest crash state is "old file or absent file, never a partial one."
  VLFS's journal exists to make exactly that sequence truthful on
  guest-owned blocks.
- **A VZ kill is a known quantity (observed).** The runner's success
  path ends in `vm.stop` (`main.swift:3123-3125`), a hard power-off
  with no guest shutdown; `--expect`/dwell reaches it from the existing
  flag surface, and `tools/gate/SPEC.md:97` says runner flags are
  passthrough — the kill gate needs at most one new knob, no harness
  change. A `stop()` throws away guest RAM, but every write the device
  *completed* is already in the host page cache, so a VZ kill proves
  journal ordering at completed-request granularity — **not** FLUSH
  correctness (that proof is class A, §D5).
- **The gate harness owns `--serial`/`--overlay-base`/`--vars`
  (observed).** `tools/gate/SPEC.md:25-26` — every `vgate_run` passes
  `--overlay-base`. The data-disk flag must coexist with it, and the
  harness's throwaway overlay covers the boot disk only.
- **Inherited bounds (observed).** `FileHandle.cursor` and `.size` are
  `u32` (`file_table.zig:97-102`) → max file 4 GiB − 1 unless the ABI is
  widened (it is not). 8 handles per process. EL0 read/write staging is
  2048 B per call (`syscall.zig:879,2023`). Path bounds:
  `directory.path_max` = 512, `name_max` = 255, `depth_max` = 8;
  directory `Entry` is a 272-B wire row. The kernel `.bss` budget is
  13,631,488 B = 13.0 MiB (`tools/verify-bss-budget.sh:53`, amended for
  issue #1163; the script's comments still say 11.0 — the constant is
  authoritative). The `.usb`/`usb_fat` partitions answer `sys_file_mode`
  with -7 (fixed policy); there is no per-file trust table outside
  `/host` (`OWNERS.TXT` lives on the share).
- **`vm.stop` is not a shutdown and ExitBootServices is not a kill
  (observed).** M92f's `live-supervise` kills a guest *process*;
  `--vz-restore` is save/restore. Neither is a power cut; the M100e gate
  uses `vm.stop` directly.

## D1. Backing device — a second virtio-blk function, identified by `GET_ID`

**Decision: virtio-blk, attached read-write by a new runner flag
`--data-disk <img>` — not `usb_msc`, and not the boot disk.**

The runner appends a second `VZVirtioBlockDeviceConfiguration` to
`config.storageDevices` in every attach mode (plain and
`--overlay-base`), setting `blockDeviceIdentifier` to the fixed string
`virelai-vlfs` (12 bytes, inside the 20-byte limit). The kernel:

1. **Pre-exit:** during the bus-0 ECAM scan, collects **every**
   function with DID 0x1042 (expect one without the flag, two with it),
   resolves each one's common/notify/device-config capability addresses
   and BAR window — the claim-0013 discipline, same as console/entropy/
   net. PCI slot order is **never** used as identity (VZ documents no
   stable order — **[inferred]**, so identity is wired, not positional).
2. **Post-rearm:** brings up one virtqueue per candidate and issues
   `VIRTIO_BLK_T_GET_ID`. The function whose identifier equals
   `virelai-vlfs` is the data disk. **Every other blk function is
   refused for writes by name** (`not_vlfs_disk`) — the boot ESP is
   unwritable by construction, and the kernel issues it no requests at
   all in normal operation (it is the firmware's volume). If GET_ID
   fails or matches nothing, there is no data disk: `no_disk`, boot
   continues share-only. VZ's actual GET_ID behavior is a claim-time
   finding for M100b **[inferred: the SDK header documents the guest
   read path; it has not been observed on the wire]**.

Rejected: `usb_msc.zig`. It works and is observed writable, but it puts
the USB topology — a second XHCI controller, enumeration order, BOT
CBW/CSW handshakes per 512 B — inside every journal commit's critical
path; VZ's sniffer refuses raw images without parseable disk structure,
so a VLFS image would need an MBR wrapper before the guest ever boots;
and under `--input` the single-controller probe can leave the disk
unreachable. A VM-native blk device has none of these costs and is the
same device class the codebase drove for years.

## D2. Host attachment and image — `--data-disk`, raw, `.full` sync

- The flag is `--data-disk <img>` (not `--disk`): the runner's
  positional argument is already the boot image, and the two must not
  be confusable. It **coexists with `--overlay-base`** — the gate
  harness always passes the overlay flag, and it covers only the boot
  disk.
- Attachment: `VZDiskImageStorageDeviceAttachment(url: img, readOnly:
  false, cachingMode: .automatic, synchronizationMode: .full)`. The
  durability contract is `.full`: a guest `VIRTIO_BLK_T_FLUSH` becomes a
  host-side full sync, the mode the SDK documents as surviving panic
  and power loss. `.automatic` caching is accepted because the
  crash-state model depends only on completed requests and FLUSH
  semantics, both governed by `synchronizationMode`, not read caching
  **[inferred: `.full`'s guarantee text is the SDK's; M100e's gate is
  the observed evidence of what it means under `vm.stop`]**.
- Image: **raw file**, size a multiple of 512 B — the only format the
  URL attachment accepts. `mkfs.vlfs` (M100c) writes it, so host tools
  can byte-assert every structure offline. ASIF is rejected: stacking
  exists to make the *boot* disk disposable; the data disk is the thing
  that must persist.
- If the flagged file does not exist the runner creates a zero-filled
  raw image (default 64 MiB, an `ftruncate` — the shape the VZ header
  itself documents) and announces it; the kernel then refuses mount
  with `not_vlfs` until `mkfs.vlfs` formats it. Formatting is the
  tool's job, never the runner's or the kernel's.
- Defense in depth, optional at M100b's discretion: the runner may also
  set the boot configuration's `blockDeviceIdentifier` (e.g.
  `virelai-boot`) so both devices are named; the write-refusal rule is
  unchanged.

## D3. On-disk format

All multi-byte integers little-endian. Every structure carries a
trailing `cksum` = **FNV-1a-32** (offset basis 2166136261, prime
16777619 — the house checksum, used by the USB gates for byte-exactness)
over all preceding bytes of its block or record. The device sector is
512 B; the VLFS allocation and journaling unit is the **block = 4096 B
= 8 sectors**. All addresses below are block numbers (`u32`) measured
from block 0 of the image.

### Volume layout

```
block 0                          superblock A
block 1                          superblock B        (ping-pong mirrors)
block 2 … 2+J-1                  journal region      (J = journal_blocks)
2+J …                            inode bitmap        (1 block)
…                                block bitmap        (bbitmap_blocks)
…                                inode table         (itable_blocks)
…                                data region         (data_blocks)
```

`mkfs.vlfs` computes J = clamp(volume_blocks/16, 512, 2048) (2–8 MiB),
`inode_count` = clamp(volume_bytes/65536, 256, 16384), `itable_blocks` =
⌈`inode_count`/32⌉ (128 B per inode × 32 per block), the block
bitmap = ⌈volume_blocks/8/4096⌉ blocks, and marks every structural block
allocated in the block bitmap at format time. (Amended 2026-10-16 from a
truncating `inode_count`/32: identical bytes whenever `inode_count` is a
multiple of 32; volumes formatted under the old rule with a remainder —
every odd-MiB size — now refuse mount with `geometry_mismatch`, which is
intended: their tail inodes aliased the data region.)

### Superblock (one 512-B sector inside each of blocks 0 and 1; rest zero)

```
+0    magic            u32   0x53464C56 ("VLFS")
+4    version          u32   1 — anything else: unsupported_version
+8    sb_seq           u64   ping-pong sequence; mount uses the highest valid
+16   volume_id        u64   random nonzero, minted by mkfs
+24   volume_bytes     u64   image size; must be a multiple of 512
+32   block_shift      u32   12
+36   volume_blocks    u32
+40   journal_first    u32   2
+44   journal_blocks   u32
+48   ibitmap_first    u32
+52   ibitmap_blocks   u32   1
+56   bbitmap_first    u32
+60   bbitmap_blocks   u32
+64   itable_first     u32
+68   itable_blocks    u32
+72   data_first       u32
+76   data_blocks      u32
+80   inode_count      u32
+84   journal_applied  u64   highest txn seq checkpointed to home blocks
+92   next_txn_seq     u64   next journal sequence number (monotonic for
                             the volume's life; minted 1 at mkfs)
+100  mkfs_time        u64   unix seconds
+108  reserved         400 B zero
+508  cksum            u32
```

Mount validates each superblock (magic, version, geometry self-
consistency, `volume_bytes` ≤ image size, cksum) and uses the highest-
`sb_seq` valid copy. Both invalid → `bad_superblock`. On every update
the new superblock is written to the slot holding the **lower** `sb_seq`
(ping-pong), so a torn write always leaves the previously-newest valid.

### Journal transaction (in the journal region, appended at the write cursor)

```
DESC block (4 KiB):
  +0    magic   u32   0x4353444A ("JDSC")
  +4    seq     u64   = superblock.next_txn_seq at commit time
  +12   n       u16   1..64 payload blocks
  +14   flags   u16   0
  +16   entry[n]      { dest_block u32, payload_cksum u32 } × n   (8 B each)
  …                 zero pad
  +4092 cksum   u32
PAYLOAD: n × 4 KiB — the complete new contents of each dest block
COMMIT block (4 KiB):
  +0    magic      u32   0x544D434A ("JCMT")
  +4    seq        u64   must equal DESC.seq
  +12   txn_cksum  u32   FNV-1a-32 over DESC[+0..+16+8n] concatenated
                         with all n payload blocks, in order
  +16   …               zero pad
  +4092 cksum      u32
```

A transaction's maximum span is n+2 = **66 blocks**; `n` > 64 marks the
record invalid. `dest_block` is an absolute block number in the data or
table regions; a `dest` outside `[2+J, volume_blocks)` or inside the
journal makes the record invalid.

### Inode (128 B; itable slot *i* ↔ inode number *i*; inode 0 never allocated)

```
+0    kind        u8    0 = free, 1 = file, 2 = directory
+1    flags       u8    0
+2    nextents    u16   0..8 inline extents
+4    size        u32   bytes, ≤ 4 GiB − 1
+8    mtime       u64   unix seconds
+16   ctime       u64   unix seconds (inode change time)
+24   extents[8]        { first_block u32, block_count u32 }
+88   next_extent_block u32   0 = none
+92   reserved    32 B  zero
+124  cksum       u32
```

Extents are dense from file offset 0 — VLFS v1 has **no sparse files**;
an extending write allocates (zeroed) blocks covering the gap inside the
same transaction. When 8 extents are insufficient, `next_extent_block`
chains an extent block:

```
Extent block (4 KiB):
  +0    magic   u32   0x42455856 ("VXEB")
  +4    next    u32   0 = end of chain
  +8    count   u16   ≤ 510
  +10   reserved u16  0
  +12   extents[]     { first_block u32, block_count u32 }
  +4092 cksum   u32
```

A file may chain at most **4 extent blocks** (bound `extent_overflow`),
so the worst-case extent list is 8 + 4×510 = 2048 entries — still a
bounded linear scan.

### Directory entry (272 B, packed inside a directory's file payload)

```
+0    inode     u32   0 = tombstone (reusable); else 1-based inode number
+4    name_len  u16   1..255
+6    kind      u8    1 = file, 2 = directory
+7    flags     u8    0
+8    reserved  u64   0
+16   name      256 B name_len bytes, rest zero
```

A directory holds at most **1024 live dirents** (`dir_full`); tombstones
are reused before growing. Root = inode 1, minted empty by mkfs (one
allocated block of zeroed dirents). `readdir` returns entries name-
sorted, matching `directory.Snapshot.sort`.

### Bitmaps

One bit per inode (`ibitmap`, `inode_count` bits, LSB-first in each
byte) and one bit per volume block (`bbitmap`); structural blocks and
inode 0 are allocated bits at mkfs. Bitmaps are metadata blocks —
mutations go through the journal like everything else.

## D4. Journal ordering and the fsync barrier

**The commit ordering (the wire contract).** Each mutating operation is
one journal transaction, committed synchronously:

1. Build DESC + PAYLOAD + COMMIT in memory.
2. Submit the three writes contiguously at the journal write cursor.
   (Ordering among them is not relied upon: the checksums make a
   half-durable record read as torn, never as valid.)
3. Submit `VIRTIO_BLK_T_FLUSH` and wait for its completion. **The
   transaction is committed exactly when this flush returns** — this is
   the line durability is measured against, and the only record whose
   durability matters for correctness.
4. Checkpoint: write each payload block to its `dest_block`, then
   FLUSH, then ping-pong the superblock with `journal_applied = seq`
   and `next_txn_seq = seq + 1`, then FLUSH, then reset the journal
   cursor to the region start.

v1 checkpoints **inside the same operation** (step 4 is not deferred):
the journal is empty at every operation boundary, reads never consult
it, and "max journal outstanding" is exactly **one transaction**.
Deferring the checkpoint is a permitted optimization only if the
implementation keeps a bounded in-memory dest→journal overlay, serves
reads through it, and honors identical ordering — flagged as a deferred
question, not a license.

**Why whole-block journaling.** Both data and metadata payload blocks
are journaled verbatim. The cost — every byte written twice — is
immaterial at this arc's workload (settings, history, opt-in user data,
2048-B staging calls). What it buys is the arc's thesis: a committed
transaction replays to a byte-exact state and an uncommitted one leaves
the home blocks *untouched*, because home writes never precede the
commit record's flush.

**The fsync barrier.** On `/disk`, every mutating call that returns
success is already committed, so `FileSync` (slot 77) issues one device
FLUSH and waits for it — a real barrier with the same caller-visible
meaning as `/host`'s fsync, and the operation `WriteFileSafe`'s
temp+fsync+rename sequence depends on. Home-block checkpointing is
**not** required for durability: the journal itself is the durable copy.

**Blocking is honest.** VLFS I/O is polled like every in-tree transport
(`virtio_custom.wait`): a `/disk` mutation or fsync **busy-waits its
core**. Each device request waits at most `blk_op_budget` =
**16,000,000** polls (the `cv_log_budget` precedent); exhaustion
refuses `io_timeout`, never a hang. Device status bytes other than
`VIRTIO_BLK_S_OK` refuse `io_error`; `UNSUPP` on GET_ID is a `no_disk`
signal, not a crash.

**`vi.WriteFileSafe` on `/disk` is unchanged.** Temp create + writes +
fsync + delete + rename are journaled commits in the pinned order;
rename still refuses a live target (`exists`), so the publish is
delete-then-rename and the honest crash state is old-file-or-absent —
identical semantics, now on guest-owned blocks. Fusing delete+rename
into one transaction is allowed, not required.

## D5. Recovery, replay, and the fsck contract

**Mount replay.** After the superblock is chosen:

1. Scan the journal from the region start. For each position, parse
   DESC: magic, `seq == expected` (starting at `journal_applied + 1`),
   `n` in range, desc cksum, each `dest` in range. Any failure → stop;
   the tail is discarded.
2. For a valid DESC, verify every `payload_cksum` and then the COMMIT
   block (magic, matching seq, `txn_cksum`, commit cksum). Any failure →
   stop; the tail is discarded.
3. For each fully valid transaction, write its payload blocks to their
   `dest_block`s (replay is idempotent — the same bytes land on the same
   blocks), advance `expected`.
4. FLUSH; ping-pong the superblock with `journal_applied = expected-1`
   and `next_txn_seq = max(next_txn_seq, expected)`; FLUSH. The max()
   rule is required: a torn superblock can roll `next_txn_seq` back over
   seqs still visible as stale journal records, and replayed state must
   never let a new transaction reuse an old seq.

**The byte-exact promise (what M100e's gate asserts).** After mount
returns success, the volume is byte-exactly the state produced by the
last committed transaction. An uncommitted tail is either absent or
refused, never silently half-present; a torn commit record truncates
the journal at that point and discards everything after it. Because
home blocks are written only at checkpoint (step 4 of D4), a crash at
any point yields one of two states — pre-transaction or post-
transaction — and replay converges both to the latter.

**`fsck.vlfs` (M100c `--check`, M100e).** Offline and read-only in v1 —
it checks, it never repairs. It validates: superblock pair and geometry
vs. the image file size; journal scan (reporting live transactions as
`journal_unreplayed` and a torn tail as the informational
`journal_torn` — expected after a kill, not corruption); inode checksums
and `kind` values; every extent inside the data region, non-overlapping,
and consistent with the block bitmap (`bitmap_inconsistent` covers
double-allocation and leaks); dirent name/kind/inode validity, tombstone
accounting, single-parent tree with root at inode 1, depth ≤ 8;
structural evaluation runs against the **as-replayed** state computed
in memory, so a clean-killed image checks what mount will deliver.
Named refusals: `not_vlfs`, `bad_superblock`, `unsupported_version`,
`geometry_mismatch`, `extent_out_of_range`, `extent_overlap`,
`bitmap_inconsistent`, `inode_checksum`, `inode_orphan`, `dirent_bad`,
`depth_overflow`, `extent_chain_corrupt`.

**What each proof layer proves (stated so no card overclaims).**

- **Class A — the ordering proof.** A crash-state enumerator in
  `zig build test` over a recording mock block device: a legal crash
  state is *every write up to the last FLUSH, plus any subset of the
  writes after it* (the device may retire same-queue requests in any
  order). For every enumerated crash image, mount+replay must yield the
  byte-exact last-committed state. This is the FLUSH-ordering proof —
  it runs without VZ, on every CI host.
- **Class B — the integration proof.** The M100e spec boots twice on
  one `--data-disk $RUN_DIR/vlfs.img`: run 01 writes payload A, fsyncs,
  prints its marker, keeps writing B, and is `vm.stop`-killed; run 02
  mounts, replays, asserts A byte-exact and B absent-or-refused. It
  proves replay and ordering on real virtual hardware **at
  completed-request granularity** — `stop()` preserves everything the
  host already accepted into its page cache, so it does **not** prove
  `.full`-mode FLUSH correctness against a host power cut. The spec
  header must say so.

## D6. Mount model — `/disk` beside `/host`, opt-in per boot

- `file_table.Partition` gains a `.disk` variant. Path canon learns the
  `disk` root in the same shape as `host`/`usb`: `/disk/…`, `disk/…`,
  `disk:…`, and bare `disk` route to `.disk` (prefix match case-
  insensitive, boundary at `/` or `:` — so `diskette.txt` stays a host
  file, the same rule that keeps `usbx.txt` on the share). Bare paths
  still land on `.host`; `/host` stays the front door and the app-
  delivery path.
- **Per-boot opt-in.** The kernel mounts `/disk` at boot only when a
  `GET_ID`-matching device is present **and** its superblock validates.
  No flag → no device → `.disk` absent. Flag but unformatted or corrupt
  → mount refuses by name (`not_vlfs`, `bad_superblock`, …) and the boot
  proceeds **share-only**: a disk is an enhancement, never a
  requirement, and a failed mount can never wedge the machine.
- **The ABI is unchanged.** Slots 23–27, 34–36, 77 behave per this ADR;
  `sys_file_mode` (69) refuses `.disk` paths -7 — v1 has **no per-file
  principal policy** off the share (`OWNERS.TXT` is a `/host` file);
  every `.disk` object is effectively world-readable/writable inside
  the guest, stated rather than hidden.
- **fs_metadata (slot 79): VLFS supplies a real `ContainedOps`
  backend.** Pins are `(inode number, ctime)` — stable by construction
  in our own format, no links exist to follow, so
  `ContainmentUnavailable` is not the honest answer here.
  `identity.filesystem` = a per-mount epoch (a kernel counter bumped on
  each mount — "nonzero, stable for that lifetime, and change on
  remount" per the `fs_metadata.zig` contract); `identity.inode` = the
  VLFS inode number.
- **No atime.** Reads never dirty the journal; `mtime`/`ctime` advance
  on mutation only. Metadata timestamps are whole seconds (matching
  `vi.Now()`'s resolution); nanosecond fields report zero.
- **Single writer.** The kernel serializes all VLFS mutations through
  the one journal; concurrent `/disk` opens are ordinary handles, and
  interleaving processes see only committed states.
- **Runtime corruption is refused, never served.** Any structure that
  fails its checksum or bounds check on the read path fails the
  operation (`bad_inode`, `bad_dirent`, `bad_extent`, `bad_journal`),
  the way `fat32_ro` latches `broken` — never a hang, never invented
  bytes.

## Non-goals (explicit)

POSIX permissions, hard links, symlinks, quotas, sparse files, atime,
multi-partition, multi-volume, online resize, directory indexes,
defrag, a writable `.usb` path, replacing `/host` as the app-delivery
path, FAT/ext compatibility, and any repair-mutating fsck. A disk is an
enhancement, never a boot requirement; `/disk` is never the default
root.

## Deferred questions

- **Deferred checkpointing.** D4 pins eager (in-operation) checkpoint.
  A bounded dest→journal overlay that batches checkpoints is a valid
  later optimization *if* it preserves the ordering and the crash-state
  contract exactly; it is a perf question, not a format question.
- **Delete+rename fusion.** `WriteFileSafe`'s publish may fuse
  delete+rename into one transaction; two transactions are equally
  correct. M100d's call, invisible to the format.
- **Boot-disk identifier.** Whether the runner also names the boot
  blk function (D2, optional) — pure defense in depth.
- **Idle-time journaling of reads.** Access-time tracking was
  considered and refused (reads must never dirty the journal); if a
  later card wants lru/atime it must amend this ADR.
- **GET_ID on VZ.** Documented in the SDK header, unobserved on our
  wire; M100b's probe records whatever is observed, and the `no_disk`
  fallback keeps a failed probe honest.
- **`.full` vs `.fsync` sync mode under a real host power cut.** The
  class-B kill gate cannot distinguish them (the page cache survives
  `vm.stop`); if a host-fault story is ever required, that needs its
  own evidence path.
