# ADR 0025: SSH — a client-first transport on the M47 primitives

Status: **ACCEPTED** · Date: 2026-09-12 · Milestone: **M51** (SSH, goal
**#1066** Stage 3) · Umbrella **#1164** · Design card **#1165** (SSH0) ·
Prerequisite cards **#1166** (SSH-P1 entropy), **#1167** (SSH-P2 OpenSSH
cipher) · Implementation cards **#1168** (SSH1 layer), **#1169** (SSH2 KEX),
**#1170** (SSH3 userauth), **#1171** (SSH4 session), **#1172** (SSH5 gate)
· Amended: 2026-09-21 (M71j / #1569 — the EL0 client is Go; `SSH.BIN` deleted)

> Fixes what "SSH" means for VirelaiOS before any SSH code is written: a
> **guest client** that dials out, the exact protocol suite built on what
> `user/src/lib/crypto/` already ships, where keys and host pins live, the
> session-encryption boundary ADR 0024 D7 left open, and the only gate
> topology the VZ-NAT runner can actually prove. Extends, and does not
> revise, ADR 0007 (syscall ABI), ADR 0020/Amendment B (net front-end),
> ADR 0022 (M46 remote seam), ADR 0023 (M47 crypto primitives), and ADR
> 0024 (M50 trust baseline). No code lands here; the binding build order
> was `ssh-scoping.md` — condensed into
> `docs/archive/era-m0-m51.md` (verbatim at its pinned SHA).

## Context

Observed on `origin/main` at `d07963c` (the M50 closeout), 2026-09-12:

1. **Goal #1066 Stage 3 is undecided between client and server.** The goal
   text says a **client** (guest SSHes *out* to real machines) is "more
   immediately useful", and that a **server** needs a VZ-NAT port-forward
   story. That story does not exist: `--net-nat` gives the guest outbound
   NAT only, and the only host→guest path today is the custom-virtio
   console (`docs/hardware-contract.md`) — not a TCP forward.
2. **The M46/M50 remote door is inbound and auth-only.** ADR 0022 fixed the
   Stage-0 host bridge (`--console-tcp`) and the Stage-1 guest remote over
   the net front-end; ADR 0024 D6 replaced the in-band shared secret with a
   delegated challenge-response, and D7 says "**No TLS, by decision** …
   ChaCha20-Poly1305 exists in M47 and is reserved for a later
   session-encryption card". That card is this ADR's boundary to close.
3. **The M47 primitives exist and are userland-only.** `user/src/lib/crypto/`
   ships SHA-256/512 + HMAC (`hmac.zig`), ChaCha20-Poly1305 (`aead.zig`),
   X25519 (`x25519.zig`), Ed25519 sign/verify (`ed25519.zig`), and
   constant-time helpers (`ct.zig`). ADR 0023 D2 forbids the kernel
   importing them. **Missing for SSH:** the `chacha20-poly1305@openssh.com`
   construction — it is *not* the RFC 8439 AEAD the library ships (see D4).
4. **There is no EL0 entropy syscall.** ADR 0024 Context 6 records slots
   0–71 (`implemented_count = 72`, `kernel/src/syscall.zig:110`); randomness
   stays kernel-side (`kernel/src/csprng.zig`), and ADR 0023 D7 and ADR 0024
   D7 both anticipate "a future userland RNG would obtain bytes via a
   syscall". SSH cannot generate an ephemeral key, a KEXINIT cookie, or
   packet padding without one.
5. **The kernel TCP seam is single-connection, bounded, and has no
   reassembly.** `payload_max = 192`, `segment_max = 212`,
   `frame_max = 246` (`kernel/src/tcp.zig:63-67`); a payload over
   `payload_max` is dropped (`:634`); when the **one-slot** RX buffer is
   full a further segment is dropped and *not* ACKed (`:765`). The userland
   client has slots 30–33 (`sys_tcp_connect/send/recv/close`,
   `kernel/src/syscall.zig:210-216`), and `sys_tcp_recv` returns at most one
   ≤192-byte chunk per call. SSH's binary packet is variable-length (up to
   ~35 KB).
6. **The runner already has both TCP directions.** `--net-tcp-respond
   <ip>:<port>[:handshake]` is a deterministic host TCP peer for a guest
   client (`host/vm-runner/Sources/VMRunner/main.swift:929`), and
   `--net-tcp-connect` is the reverse (`:953`); the `--net` emulation is
   how every net gate stays hermetic. The M46 `vgate_client` hook drives a
   host→guest client, not a guest→host one.
7. **The M50 key store is the only secret surface, and it is read-only from
   the guest.** `SECRETS.TXT` (`max_key_len = 32`, `max_val_len = 64`,
   `#v1`; ADR 0024 D8) is readable only through `sys_secret_get` (slot 70);
   there is **no `sys_secret_set`** — the host provisions by editing the
   share file, and the file ABI cannot read a secret at all.

The question this ADR answers: *what is the smallest real SSH that the
current kernel seam and runner can prove, and what is it allowed to claim?*

## Decision

### D1. Client-only for M51; the server is explicitly deferred
M51 builds an SSH-2 **client**: the guest opens a TCP connection out to a
host and lands an authenticated, encrypted session. This is the direction
goal #1066 prefers, and the only one the runner can test deterministically
today (`--net` + `--net-tcp-respond`, Context 6). An SSH **server** is
deferred until a VZ-NAT host→guest port-forward story (or a custom-virtio
TCP bridge) exists; when it lands it additionally needs a guest host key, an
`authorized_keys` analogue, and inbound-reachability proof. The ADR records
the server as out of scope rather than pretending the direction is neutral.

### D2. The protocol suite: one modern profile, and nothing else
M51 offers exactly one of each negotiation list, so interop is honest and
the parser stays small:

| Role | Algorithm | Why |
|---|---|---|
| Transport | SSH-2.0 (RFC 4253) | The only protocol version in use |
| KEX | `curve25519-sha256` (RFC 8731), alias `curve25519-sha256@libssh.org` | X25519 + SHA-256, both shipped; the alias keeps older OpenSSH interop |
| Host key | `ssh-ed25519` (RFC 8709) | `ed25519.verify` shipped; no RSA/ECDSA bignum exists |
| Cipher | `chacha20-poly1305@openssh.com` | Built on shipped ChaCha20/Poly1305 (D4); no AES in the tree |
| MAC | *(none — AEAD)* | The cipher authenticates each packet |
| Compression | `none` | No compressor, and none wanted |
| User auth | `publickey` with `ssh-ed25519` (RFC 4252 §7) | One identity, one signature |

The client offers **only** these. Rejected for M51: `diffie-hellman-group*`
and `ecdh-*` (no bignum / no NIST curves), `ssh-rsa`/`rsa-sha2-*` and
`ecdsa-*` host keys, AES-GCM/CTR/`hmac-*` ciphers and MACs, password and
keyboard-interactive auth (no echo-safe input path, and no need),
`ssh-agent`, X11/port forwarding, SCP/SFTP, and certificates/user
`cert-authority` (no CA). These are omissions with reasons, recorded in
`ssh-scoping.md` (condensed into `docs/archive/era-m0-m51.md`, verbatim at
its pinned SHA).

### D3. Key sources: secret identity in TS5, public pins in a share file
The two kinds of key material have opposite confidentiality needs, so they
live in the two different stores M50 already built:

- **The client's private key** is secret and never leaves userland. It is a
  32-byte Ed25519 seed stored as **64 hex chars** under the TS5 secret key
  **`ssh-user-ed25519`**, read with `sys_secret_get` (slot 70) and zeroized
  (`ct.wipe`) after use. The name (16 chars) and value (64 chars) fit the
  store's `max_key_len = 32` / `max_val_len = 64` bounds exactly (ADR 0024
  D8). Provisioning is **host-side** by editing `SECRETS.TXT` (the entry is
  `ssh-user-ed25519<TAB>1000<TAB><64-hex-seed>`, scoped to `uid_user`);
  there is no `sys_secret_set`, and the never-logged contract applies.
- **Host-key pins** are public and must be human-editable and inspectable.
  They live in a plain share file **`SSH/KNOWN_HOSTS`** in the project's
  bounded `#v1` line form (`host<TAB>port<TAB>ssh-ed25519<TAB><hex-pubkey>`),
  read through the ordinary file ABI (slots 23–27). A plain file is
  deliberate: `SECRETS.TXT` is the secret class the file ABI denies, which
  would make pins unauditable and impossible to seed from tooling. No
  OpenSSH `known_hosts` base64 format in M51 — base64 is a small codec that
  a later card can add if real file interop is wanted.
- **Ephemeral KEX keys** are generated fresh per session from D5's entropy
  syscall and never stored.
- The M50 **`net-hmac` / `net-ed25519`** keys are the *inbound remote door*
  (the guest as server) and are **not** reused as SSH identities. When the
  server direction lands it gets its own `ssh-host-ed25519` secret and an
  `authorized_keys`-style share file.

### D4. The one missing primitive is the OpenSSH cipher, and it is a prerequisite
`chacha20-poly1305@openssh.com` is **not** RFC 8439 ChaCha20-Poly1305.
It uses the original djb ChaCha20 (a **64-bit nonce** — the SSH packet
sequence number — and a 64-bit counter), splits the 64-byte key, encrypts
the 4-byte length under one half and the payload under the other, and
authenticates `encrypted_length ‖ encrypted_payload` Encrypt-then-MAC. The
shipped `crypto/aead.zig` has the RFC 8439 nonce/counter and MAC layout and
**cannot be called for SSH**; the shipped `chacha20.block` takes a 12-byte
nonce and cannot either. This is a prerequisite card (**SSH-P2 #1167**), not
an assumption: add `crypto/chacha20_ssh.zig` (djb 64-bit nonce/counter,
KAT-pinned) and `crypto/ssh_cipher.zig` (the OpenSSH construction), with the
OpenSSH `PROTOCOL.chacha20poly1305` test vector. **Hazard recorded for the
implementer:** the IETF `draft-ietf-sshm-chacha20-poly1305` names K_1/K_2
inverted relative to the authoritative OpenSSH file; implement to the
OpenSSH file and pin its vector. `crypto/aead.zig` stays as the RFC 8439
primitive (it is not dead code — it is simply the wrong construction here).
The rest of the suite is assembly work over shipped primitives: KEX is
`x25519.scalarmult` + `sha256`, host-key and userauth are `ed25519.verify` /
`ed25519.sign`, and constant-time compares are `ct.ctEq`.

### D5. Randomness: one new syscall slot, `sys_getrandom`
The client needs fresh bytes for the ephemeral X25519 secret, the KEXINIT
cookie, and per-packet padding. The kernel already owns the CSPRNG
(`csprng.random_bytes`, used by ADR 0024 D6 to mint the auth challenge), so
M51 exposes it read-only:

- **ADR 0007 slot 72 `sys_getrandom(buf, len)`**: fills caller memory from
  `csprng`, `len` capped at a bounded maximum, `EFAULT` on a bad buffer,
  `len == 0` returns 0; no new capability (every principal may read
  entropy). `implemented_count` 72 → 73; ADR 0007's table and the count are
  updated by the card.
- **M97g amendment (issue #2084): fail closed while unseeded.** The D5
  contract silently served the deterministic `seed_fallback` stream when
  the host entropy device was absent or reset — reproducible bytes indi-
  stinguishable from real entropy. Slot 72 now returns `EAGAIN` (-11) and
  writes nothing while `!csprng.seeded()`, retrying the device read (with
  one transport re-arm) inside the refusal path — the boot seed is no
  longer the only reseed opportunity. Consumers that need entropy must
  tolerate the transient refusal; a boot log line still reports honestly.
- This is **the only new syscall M51 adds.** Every other card adds zero
  slots. The kernel stays crypto-free (ADR 0023 D2): it does not import the
  M47 library, does not do field arithmetic, and does not touch an SSH
  packet — it only returns bytes and moves bytes.

The slot is its own prerequisite card (**SSH-P1 #1166**) because the KEX
cannot be tested without it.

**Shared slot (coordination).** `sys_getrandom` is not SSH's alone: the
GOOS=virelai runtime port (**#1163**) needs the same primitive for the Go
runtime's hash seed. To avoid two entropy slots, **slot 72 is a single
shared contract** — SSH-P1 owns and lands it; the Go runtime consumes it
(and if the Go port lands first it implements slot 72 to this contract and
SSH-P1 reduces to the `lib/rng.zig` wrapper). The Go port's later
`thread_create`/`futex` slots then append at 73/74. This keeps ADR 0007
append-in-order and `implemented_count` honest.

### D6. The userland stream adapter is mandatory, and the kernel seam is not changed
The kernel's one-slot, 192-byte, no-reassembly TCP RX (Context 5) cannot
deliver a variable-length SSH packet. M51 does **not** change the kernel TCP
stack; it adds a userland **stream adapter / packet layer** (**SSH1 #1168**)
that:

- keeps a bounded caller-owned (static BSS) buffer, concatenates complete
  in-order ≤192-byte chunks, and parses RFC 4253 binary packets; a packet
  over the fixed in-tree cap or a ring overflow **fails closed** (disconnect)
  — never truncate-and-continue;
- **drains promptly**: loops `sys_tcp_recv` to exhaustion before heavy work,
  so the kernel's one slot is emptied and the next segment is accepted, and
  paces TX to at most one outstanding segment (send, then drain until the ACK
  clears `tx_pending`) because the kernel's retransmit buffer holds one
  segment.

Honest limits this creates and that the scoping doc states: a segment that
arrives while the slot is full is dropped and **not ACKed**, so end-to-end
correctness leans on the peer's TCP retransmission of that segment; the
resulting throughput ceiling is segment-at-a-time; and the kernel does not
validate RX sequence numbers, so the adapter assumes the peer's TCP
in-order guarantee. A **bounded kernel RX ring** would remove the ceiling
and is a plausible future amendment, but it changes the "single-connection,
no-reassembly" contract and is deliberately **not** in M51.

### D7. M51 provides session confidentiality — unlike the M50 remote door
ADR 0024 D7 left open whether a session-encryption card would exist. This
ADR closes it for SSH:

- **Provided:** after `SSH_MSG_NEWKEYS`, every SSH packet is encrypted and
  authenticated with `chacha20-poly1305@openssh.com`; the session key comes
  from an ephemeral X25519 exchange, so the session has **confidentiality**,
  **integrity**, and **forward secrecy** against a later compromise of the
  static keys, and the fresh KEX + host-key pin gives **server
  authentication** to the pinned key. A captured SSH session is not
  replayable into a new one (fresh ephemeral keys + `session_id`).
- **Not provided, by decision:** the M50 remote door (ADR 0022/0024) is
  **unchanged and still plaintext** — M51 does not encrypt it; the **server**
  direction does not exist (D1); no password or keyboard-interactive auth;
  no `ssh-agent`, port forwarding, SCP/SFTP, X11, or certificates; no
  **rekey** (a session that hits the documented bound of **1 GiB or 2^20
  packets per direction, whichever comes first**, disconnects with
  `SSH_MSG_DISCONNECT` reason 11 and reconnects — honest, not silent, and
  implemented in `ssh/transport.zig`); no protection against a compromised
  host or a wrong/absent known-hosts pin beyond refusing the host key; and
  no side-channel guarantee beyond ADR 0023 D3's stated constant-time
  discipline. The M51 client is a *transport*, not a trust upgrade for the
  inbound door.

### D8. Gate topology: client direction, a deterministic runner-hosted responder
The guest is behind VZ NAT, so the testable direction is **guest → host**,
with the **runner hosting the peer** (Context 6). SSH5 (#1172) extends the
existing deterministic `--net-tcp-respond` responder into a minimal SSH-2
**server** (`…:ssh`): `curve25519-sha256` KEX with a pinned `ssh-ed25519`
host key, pinned `publickey` acceptance, one session channel, one fixed
`exec`. The guest runs `SSH.BIN` against it; the gate asserts guest serial
markers plus responder output. Negative runs: unknown host key refused,
wrong user key refused, tampered packet MAC disconnected, missing credential
fails closed. Because the responder is Swift/CryptoKit and the client is
Zig, the two cipher implementations are tied by **the same pinned vectors**
— the ADR 0023 D2 drift-guard pattern, applied host-side.

A **real-OpenSSH interop** run (the host's `sshd`/a container, reached over
`--net-nat`, or a manual observation) is recorded as a documented check, not
a CI gate: CI cannot guarantee an SSH endpoint. The custom-virtio bridge is
the fallback if a Swift cipher is rejected in review; it is not the first
choice because it would not exercise the real TCP path.

**SSH5 implementation status (2026-09-12).** The Swift cipher was **not**
rejected: `host/vm-runner/Sources/VSSH/` carries a hand-rolled djb
ChaCha20 + Poly1305 + the OpenSSH split-key construction, a **startup
self-check** that refuses to arm `:ssh` unless it reproduces SSH-P2's pinned
`PROTOCOL.chacha20poly1305` vector, and `swift test` class-A tests pinning
the same vectors plus `kex.zig`'s deterministic transcript (RFC 7748 §6.1
X25519, RFC 8032 §7.1 host key, H and the KDF keys). CryptoKit Ed25519 uses
a hedged nonce (observed: two signatures differ per call), so the host-key
tie is **verification** of the Zig/OpenSSL-pinned signature over the pinned
H, not byte equality of new signatures. VMRunner wires `:ssh` into the
capture thread and paces one encrypted ≤192-byte segment per guest ACK (the
`:packet` mechanism; the guest kernel RX is a single slot with no
reassembly). The gate exposed and SSH5 fixed **two latent client wire
bugs**: SSH3 sent the `string session_id` prefix **on the wire** in the
`publickey` request (RFC 4252 §7 signs it but does not send it), and the
channel layer expected a 1-byte `CHANNEL_EOF` (RFC 4254 §5.3 carries a
recipient channel). Live class-B: `live-ssh-endpoint` (KEX + pinned host
key + `publickey` + one `session` exec with the deterministic marker and
`exit-status`), `live-ssh-negative` (unknown pin refused before any
userauth; wrong user key `AuthRejected`; tampered MAC `protocol` fail
closed), `live-ssh-nocred` (`MissingCredential`, fail closed) — all PASS.
**Real-OpenSSH interop (issue #1209, 2026-09-12): transport proved, one
conformance gap observed.** VZ-NAT guest→host TCP is confirmed impossible
on this host, not assumed: while the VM ran, no host interface carried the
guest subnet (`vmenet0` was inactive with no address; no host route or ARP
entry for 192.168.64.0/24), the gateway is a Virtualization.framework
internal router (a synthetic MAC answered ARP and ICMP), the macOS
application firewall was OFF, and `sshd` bound `*:2222` at DEBUG3 logged
**no** connection while the guest's own `net tcp connect` sat in SYN_SENT.
The check therefore ran through a new **byte-transparent runner relay**
(`--net-tcp-respond <ip>:<port>:relay` + `--net-tcp-respond-relay
127.0.0.1:2222`; the runner does no crypto) against the host's real
`/usr/sbin/sshd` (OpenSSH_10.3p1, LibreSSL 3.3.6) with a generated host
key pinned in `SSH/KNOWN_HOSTS` and the RFC 8032 TEST 2 client key in
`authorized_keys`. **Observed:** the guest's `SSH.BIN
tbuddy@10.0.0.2:2222 echo VIRELAI-INTEROP-OK` negotiated
`curve25519-sha256` + `ssh-ed25519` + `chacha20-poly1305@openssh.com` (no
compression) and **verified the real server's host-key signature**
(`ssh: kex-ok`); real sshd then rejected the first encrypted packet
(`SSH2_MSG_SERVICE_REQUEST`) with `padding error: need 28 block 8 mod 4`,
`SSH2_MSG_DISCONNECT: Packet corrupt`, and `message authentication code
incorrect`, so userauth, the exec stdout and `exit-status` were **not**
observed. **Root cause (verified against openssh-portable `packet.c`):**
for `chacha20-poly1305@openssh.com` OpenSSH pads so `packet_length` — the
encrypted part *after* the 4-byte length field — is a multiple of the
cipher block size, while the client (and the VSSH responder) aligned
`4 + packet_length` (the RFC 4253 §6 total-includes-length rule, which is
correct for the plaintext KEX packets and is why KEX completed). The fix
is follow-up claim **#1210** (client `packet.zig`/`transport.zig` + VSSH
realignment + class-A vectors); it was deliberately not smuggled into the
evidence change. The client seed never appears in the serial, runner, or
sshd logs. No kernel changes; the boot default is unchanged (the
responder-adjacent fleet re-run green).

**Real-OpenSSH interop FIXED (claim #1210, 2026-09-12): KEX + userauth +
remote stdout + `exit-status` observed end to end.** The alignment is now
selected by the cipher via `packet.Alignment`, never a global constant:
`.plaintext` (`(4 + packet_length) % 8 == 0`, RFC 4253 §6) for every KEX
packet, `.aead` (`packet_length % 8 == 0`, OpenSSH `packet.c`
`ssh_packet_send2_wrapped`) for `chacha20-poly1305@openssh.com`; the VSSH
responder mirrors the split and its startup drift guard additionally pins
the OpenSSH frame (`packet_length 0x48` accepted only under `.aead`). Two
further client bugs surfaced once userauth got through, both fixed with
class-A vectors: (1) OpenSSH sends `hostkeys-00@openssh.com` (a
GLOBAL_REQUEST **with** request-specific host-key data) between userauth
success and `OPEN_CONFIRMATION`, so `channel.open()` now skips global
requests — RFC 4254 §4 says unhandled request data is ignored — and answers
`want_reply` with `REQUEST_FAILURE`; (2) OpenSSH confirms its first session
channel with **sender id 0**, so `remote_id == 0` can no longer mean
"unset" (explicit `remote_set`). Observed against the same real
`/usr/sbin/sshd` (OpenSSH_10.3p1) over the `:relay` bridge, raw evidence in
`artifacts/m51-interop/runs/relay-06/`: `SSH.BIN tbuddy@10.0.0.2:2222 echo
VIRELAI-INTEROP-OK` → `ssh: kex-ok` → `ssh: pin-ok` → `ssh: auth-ok
method=publickey` → `ssh: channel-open remote=0` → remote stdout
`VIRELAI-INTEROP-OK` → `ssh: eof` → `ssh: exit-status=0` → `ssh: bye
rc=0`; sshd's DEBUG3 log shows `Accepted publickey`, the `exec` request and
`exit-status 0`. The seed appears in no log. No kernel change; the boot
default is unchanged; `live-ssh-endpoint` 1/1, `live-ssh-negative` 3/3 and
`live-ssh-packet` PASS re-ran green with the realigned responder.

### D9. Verification is two-class, and the boot default does not move
- **Class A:** pure, injected-seam tests (`netauth.zig`'s `Ops`/`Source`
  pattern) — wire codec round-trips, packet/length bounds, split-packet
  reassembly and overflow fail-closed, KEX vectors, host-key/user-auth
  rejection, channel state machine — plus the crypto KATs (D4) and the
  `sys_getrandom` bounds.
- **Class B:** one declarative spec per property under `tools/gate/specs/`
  (AGENTS.md M40 GF6), e.g. `live-ssh-kex`, `live-ssh-auth`,
  `live-ssh-exec`, plus the negative specs; discovered, not listed. The
  inventory is regenerated by SSH5.
- **Boot default unchanged:** `SSH.BIN` is only run when asked, no SSH code
  is on the boot path, `sys_getrandom` is registered but not called at boot,
  and the existing class-B fleet keeps passing.

### D10. Card split, one syscall slot at most
| Card | Deliverable | Slots |
|---|---|---|
| **SSH0** #1165 (this ADR) | ADR 0025 + `ssh-scoping.md` (docs only; condensed into `docs/archive/era-m0-m51.md`) | 0 |
| **SSH-P1** #1166 | EL0 entropy `sys_getrandom` (slot 72) + `lib/rng.zig` | **+1** |
| **SSH-P2** #1167 | `chacha20-poly1305@openssh.com` construction + KATs | 0 |
| **SSH1** #1168 | wire codec + binary packet/stream layer over `sys_tcp_*` | 0 |
| **SSH2** #1169 | KEX `curve25519-sha256` + NEWKEYS + `ssh-ed25519` verify | 0 |
| **SSH3** #1170 | userauth `publickey` (ed25519) + key/known-hosts store | 0 |
| **SSH4** #1171 | session channel + pty/exec (`SSH.BIN`) | 0 |
| **SSH5** #1172 | class-B endpoint gate + runner SSH responder | 0 |

Order: SSH1 and SSH-P1 and SSH-P2 may proceed in parallel after SSH0;
SSH2 needs all three; SSH3 needs SSH2; SSH4 needs SSH3; SSH5 needs SSH4.
Every card presents `boot-default-unchanged` evidence (the existing class-B
suite green). The scoping doc carries the acceptance detail.

**Implementation status (2026-09-12).** SSH-P1 (slot 72 + `lib/rng.zig`),
SSH-P2 (`crypto/chacha20_ssh.zig` + `crypto/ssh_cipher.zig`) and SSH1
(`ssh/wire.zig`, `ssh/packet.zig`, `ssh/stream.zig`) are merged. SSH2
(#1169) adds `ssh/kex.zig`: the version exchange, KEXINIT single-suite
negotiation, `curve25519-sha256`, `ssh-ed25519` host-key verification, the
exchange hash H, the RFC 4253 §7.2 KDF (64-byte cipher key; the AEAD's IV
is empty because its nonce is the packet sequence number) and NEWKEYS with
cipher install; `session_id = H` is exposed for SSH3. RFC 8731 publishes no
full-KEX vector, so the class-A proof pins K from RFC 7748 §6.1 and pins H
and the KDF keys from an independently computed deterministic transcript
(OpenSSL-signed host key); negatives cover a wrong signature, a tampered H,
a wrong `session_id`, unnegotiable peers and malformed packets. No kernel
changes; boot default unchanged. SSH3 (#1170) adds `ssh/userauth.zig`: the
`SSH/KNOWN_HOSTS` `#v1` parser and the fail-closed pin check against the
KEX-verified host key **first** (nothing is sent and no secret is read
before the pin is proven), the `ssh-userauth` service request/accept
exchange, the `none` probe, and the `publickey` ed25519 request whose
signature covers `string session_id || byte 50 || string user || string
"ssh-connection" || string "publickey" || boolean TRUE || string
"ssh-ed25519" || string key_blob` (RFC 4252 §7). The client seed is read
from the TS5 `ssh-user-ed25519` entry through `sys_secret_get` (slot 70)
only once `none` is refused, and every staging buffer (hex credential,
decoded seed, signature) is `ct.wipe`d on every path; the seed never
appears in any captured output. Distinct fail-closed statuses cover a
missing/absent pin, a pin mismatch, a missing or malformed credential, no
`publickey` offer, and a rejection; the signed-byte layout is asserted
byte-for-byte against a signature pinned by OpenSSL Ed25519, and the
request is refused before any packet when the pin or the `h`/`session_id`
handoff does not check out. The transport seam carries decrypted payloads;
the encrypted packet layer over `kex.Result.send/recv` lands with SSH4's
`SSH.BIN`. No kernel changes; boot default unchanged. SSH4 (#1171) adds
`ssh/transport.zig` — the encrypted packet layer SSH3 deferred: RFC 4253 §6
framing over `packet.zig`, sealed/opened with the KEX-installed OpenSSH AEAD
(`enc_length(4) ‖ enc_payload(packet_length) ‖ tag(16)`; the length is
decrypted first with `ssh_cipher.decryptLength`, the tag is verified before
any plaintext is trusted, and the cipher sequence numbers continue across
NEWKEYS — the class-A test pins the handoff at 3 and shows a peer that reset
to 2 cannot authenticate) — plus the no-rekey bound (1 GiB / 2^20 packets
per direction), which sends `SSH_MSG_DISCONNECT` reason 11 and closes; a
DISCONNECT from the peer ends cleanly. `ssh/channel.zig` adds the RFC 4254
session channel: `SESSION` open with `OPEN_CONFIRMATION`/`OPEN_FAILURE`,
exact window accounting (data in chunks of
`min(remote window, remote max packet)`, `WINDOW_ADJUST` emitted when our
advertised window falls to half, zero-window exhaustion and over-window data
both fail closed), `pty-req` (§6.2, optional), `exec`/`shell` (§6.5) with
`CHANNEL_SUCCESS`/`FAILURE`, `DATA`/`EXTENDED_DATA` (stderr surfaced), `EOF`
and `CLOSE` (answered exactly once), and the server's `exit-status` /
`exit-signal` requests with unknown requests answered `CHANNEL_FAILURE`.
`user/src/ssh.zig` → `SSH.BIN` (DSK3 segmented, static BSS) wires the stack:
numeric-IPv4 target `[user@]host[:port] [cmd]` → `sys_tcp_connect` →
`kex.Kex.run` → pin + `userauth` → channel → one-shot `exec` (exit with the
remote `exit-status`; 255 when the peer sends none) or interactive `shell`.
Interactive local input reuses **existing** surface, not new kernel surface:
the `/dev/tty` file ABI (slots 23/24/26) plus slot 67's serial attach, with
the raw queue pumped as `CHANNEL_DATA` (the `SH.BIN` pattern). DNS hostnames
are a documented later slice: a non-literal target fails usage. Every serial
marker is one `sys_write`. `ssh/cli.zig` carries the pure CLI grammar and its
class-A tests. No kernel changes; boot default unchanged. SSH5 (#1172) landed
the class-B endpoint gate and the runner-hosted responder (see D8); the two
wire bugs that gate caught in SSH3/SSH4 are fixed in place
(`ssh/userauth.zig` sends the RFC 4252 §7 packet without the signed
`session_id` prefix; `ssh/channel.zig` parses the RFC 4254 §5.3
`CHANNEL_EOF` recipient), and the class-A vectors were re-pinned to the
correct wire layouts.

## Consequences

- The M47 library gains its second live consumer (after `CRYPTOD.BIN`) and
  one new construction; the kernel gains exactly one syscall slot (73 total)
  and remains crypto-free.
- The bounded TCP seam stops being just an HTTP/remote-console transport: a
  userland layer can carry a real variable-length protocol over it, at a
  documented throughput ceiling and with an explicit "TCP retransmits the
  dropped segment" correctness argument.
- ADR 0024 D7's open session-encryption question is answered: SSH is the
  session-encryption card; the M50 inbound door is explicitly *not* it.
- The client-vs-server question is answered for M51: client only, with the
  server blocked on a port-forward story, so no card builds a listener.
- Key material is split by need (secret seed in TS5, public pins in a share
  file); provisioning stays host-side, with no `sys_secret_set`.
- Risk: the runner's Swift SSH responder may reimplement the OpenSSH cipher;
  the drift-guard vectors make that a pinned duplication rather than an
  untracked one (ADR 0023 D2 precedent).

## Rejected alternatives

- **Server-first (host SSHes into the guest).** Needs a VZ-NAT port forward
  that does not exist, plus a guest host key and `authorized_keys`; not
  testable today and not the goal's preferred direction (D1).
- **TLS instead of SSH.** ADR 0024 D7 rejects TLS; SSH is the named goal and
  its primitives are already shipped (D2).
- **A custom encrypted remote console with ChaCha20-Poly1305.** Smaller, but
  it is not SSH and does not interoperate — it would answer "remote in" for
  the guest-as-server direction that has no reachability story anyway.
- **The RFC 8439 AEAD as the SSH cipher.** Wrong nonce/counter width and MAC
  layout; it would not interoperate and would be a silent protocol bug (D4).
- **A bounded kernel RX ring now.** Would remove the segment-at-a-time
  ceiling but changes the no-reassembly contract; deferred as a future
  amendment, not smuggled into SSH (D6).
- **RNG-derived-from-secret ephemeral keys (no entropy syscall).** Reused
  ephemeral keys destroy forward secrecy; the one-slot `sys_getrandom` is
  the honest prerequisite (D5).
- **OpenSSH base64 `known_hosts` format now.** Adds a base64 codec and a
  parser for zero first-target benefit; the `#v1` hex file is auditable
  (D3).
- **Rekeying in M51.** Real work with no first-target driver; the client
  disconnects at a documented bound instead, recorded as an open issue
  (D7).

## Open issues

- VZ-NAT host→guest port forwarding (or a custom-virtio TCP bridge) — the
  precondition for the deferred SSH **server**.
- Rekeying (RFC 4253 §9) once sessions are long-lived.
- Base64 / OpenSSH-format `known_hosts` and `authorized_keys` interop.
- A bounded kernel TCP RX ring, if the segment-at-a-time ceiling bites.
- Multi-connection TCP (the single-connection stack shared with the M46
  remote door).
- Which principal an SSH session runs as, and whether SSH keys should be
  per-principal beyond the TS5 `uid` scoping (ADR 0024 D8).
- A userland RNG service/`getrandom` batching if per-packet padding makes
  the per-call syscall cost visible.

## Amendment: M70g G1 (#1491) — the deferred server lands in-guest

Amended 2026-09-19. D1 deferred the SSH **server** until inbound TCP was
testable. That inbound path already exists: `--net-tcp-connect` (ADR 0020
Amendment B) initiates host→guest TCP over the same `--net` attachment
the M51 client used in the other direction. G1 is the in-guest SSH-2
server (`GOSSHD.ELF` in `user/go/sshd/`):

- `vi.Listen` / `Accept` over the existing slot-30 passive open (`ip==0`);
  no new ADR 0007 row.
- The D2 profile with the roles reversed: `curve25519-sha256` KEX,
  `ssh-ed25519` host key from TS5 **`ssh-host-ed25519`**, `publickey`
  against share file **`SSH/AUTHORIZED_KEYS`** (`#v1` /
  `user\tssh-ed25519\t<hex>`), one `session` `exec`.
- A session command is `GOSH.ELF -c '<command> > SSH/EXEC.OUT'` (ADR 0007,
  M71m #1572). The argv slot is 255 bytes; a longer line is refused.
  `SSH/EXEC.IN` is not used.
- The runner hosts the **client** (`VSSH.SSHClient` behind
  `--net-tcp-connect <guest-ip>:<port>:ssh`), paced one ≤192-byte
  segment per guest ACK. Class-B gate: `live-ssh-server`.
- No new ABI, no boot-default change, no port forwarding / agent / SFTP.
  D1's "client-only for M51" stands; this amendment is the server
  direction M51 recorded as deferred.

The M51 client (`SSH.BIN`) and the runner-hosted responder
(`--net-tcp-respond …:ssh`) are unchanged.

## Amendment: M71j (#1569) — the EL0 client is Go

Amended 2026-09-21. ADR 0030 left `SSH.BIN` "until its own Go card."
That card is this one. The D2 profile does not move; the language of
the EL0 client does.

- **The EL0 SSH-2 client is `GOSSH.ELF`** (`user/go/ssh/`). It dials
  outbound over `vi.Dial`, speaks D2 (`curve25519-sha256`,
  `ssh-ed25519`, `chacha20-poly1305@openssh.com`, `publickey`, one
  session `exec`), and fails closed with the same stage/exit numbers
  M51 pinned (`HostKeyMismatch` rc=4, `AuthRejected`/`MissingCredential`
  rc=5, protocol rc=8). Serial markers are unchanged, so the three
  client gates (`live-ssh-endpoint`, `live-ssh-negative`,
  `live-ssh-nocred`) retarget by staging `.build/go/GOSSH.ELF` instead
  of `SSH.BIN`.
- **Primitives are reused, not rewritten.** KEX, AEAD, Ed25519, and
  the packet codec live in `user/go/sshlib/` — the same crate
  `GOSSHD.ELF` already used in-tree under `user/go/sshd/`. ADR 0023
  D2 stands; this card does not invent a second cipher.
- **`SSH.BIN` and `user/src/ssh.zig` are gone**, with the Zig client
  modules (`lib/ssh/{kex,userauth,transport,channel,cli}.zig`) that
  nothing else linked. `lib/ssh/{wire,packet,stream}.zig` stay: they
  are the `SSHPACKET.BIN` stream-adapter proof (`live-ssh-packet`).
  That is the TLS-helper shape (M71k): the product binary leaves; the
  host-side / packet-layer proof that still has a consumer stays.
- **GOSSHD is not this card.** D1's server (M70g G1, `#1491`) stays
  `GOSSHD.ELF`. No argv lift, no POSIX `ssh` flag surface, no catalog
  row (`APPS.TXT` never listed `SSH.BIN`; it does not list `GOSSH.ELF`).
- **Boot default unchanged.** `GOSSH.ELF` is only run when asked.

## Amendment (2026-10-21, #2960) — the sans-IO server serves an interactive session

Amended 2026-10-21. The M70g G1 channel layer covered one `session`
`exec` and refused everything else. #2960 grows it into one interactive
session per connection so GOSSHD can host a TUI (#2961) without a
second SSH implementation beside the D2 stack:

- **`pty-req`** (RFC 4254 §6.2) parses TERM, cols/rows, pixel size and
  the raw terminal-modes stream, granted once and before `shell`.
  **`shell`** (§6.5) answers CHANNEL_SUCCESS only on a granted pty:
  a shell with no pty, a second shell, a pty-req or an `exec` after the
  shell all get CHANNEL_FAILURE. `exec` itself is unchanged.
- **`window-change`** (§6.7) decodes into a resize event. Inbound
  CHANNEL_DATA queues for the app behind `Server.Drain` — data,
  resizes and the client's EOF in wire order — with local window
  accounting: the input queue is bounded by the advertised
  `LocalWindow`, a peer that overruns it fails the transport closed,
  and `Drain` returns the credit (WINDOW_ADJUST) once half the window
  has been consumed.
- **Outbound** is `Server.Write`: it seals what the remote window and
  the peer's max packet admit and keeps the rest queued until
  WINDOW_ADJUST — nothing dropped. `Server.CloseSession(status)` sends
  exit-status, EOF and CLOSE exactly once.
- The session is served **by the GOSSHD process itself** — no child
  shell. No new ABI, no boot-default change, the D2 profile unchanged,
  and still no port forwarding, agent or SFTP. One channel per
  connection stands.
